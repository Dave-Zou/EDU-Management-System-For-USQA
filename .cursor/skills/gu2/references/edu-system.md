# 教务管理系统作为 GU2 产品

仓库：`EDU-Management-System-For-USQA`。产品是一个学校成绩与课表的 Web 应用。下面的对照在编写 skill 时读过 `src/`。写任何交卷句子之前，重新打开对应文件。`.trae/documents/prd.md` 和 `technical-architecture.md` 落后于代码（状态管理写成了 Context，实际是 Zustand；申诉、考试、用户管理、学生注册已在代码里）。

## 技术事实（开发环境与非功能需求）

- 界面与问题域目前都在浏览器里：React 18、TypeScript、Vite、Tailwind CSS、React Router 6、Zustand（`persist` 到 `localStorage`）。
- 没有独立后端。`technical-architecture.md` 里的 `/api/*` 是设想，不是已实现的接口。
- 账号数据来自 `src/data/mockData.ts`，口令字段在客户端用户对象上。
- 登录入口把身份分成学生 / 老师 / 教务。老师身份同时接受 `teacher` 和 `homeroom_teacher`（`src/store/useStore.ts` 的 `login`）。

这些限制写进非功能需求和评估。它们是范围，不是还没来得及说的实现。

## 建议纳入本次范围的用户目标

顶层用例用动词短语，一个椭圆一件用户的事：

3. View grades
4. Record a grade
5. Review a grade
6. Appeal a grade
7. Resolve an appeal
8. View the timetable
9. Arrange a class

若时间不够，在计划里把范围收成一条主链并写明排除项。建议的主链是：**任课老师登记成绩 → 班主任或教务复核 → 学生查看 → 学生申诉 → 相应角色处理申诉**。排课、考试、用户管理可以保留在用例图上，但要在计划里标明它们是同一产品里的次要用例，并保证每条保留的用例至少有一条测试。

不要把「打开成绩列表页」「点击保存按钮」画成用例。

## 主场景（五张图都要走得通）

场景名：**Record and review a grade**。

1. 任课老师登录（身份选老师）。
2. 选择课程、班级和学生，录入分数。系统算出等级，状态为待复核。
3. 非法分数被拒绝（失败路径，活动图和测试都要有）。
4. 班主任或教务打开待复核列表，通过或退回，并可写评语。
5. 学生只能看到自己的成绩和复核结果。

沿这条场景核对：

- 用例：Record a grade、Review a grade、View grades。
- 名词分析留下的类至少包括 Grade、Student、Course、SchoolClass、Teacher、Review。界面、按钮、`localStorage` 丢进「舍弃」，并写理由。
- CRC 的职责是完整句子。Grade 自己知道分数是否在满分以内、等级如何从分数得出；复核决定放在最了解复核状态的类上。
- 类图上的操作能在 `src/store/useStore.ts` 或抽出来的领域模块里指出对应函数（`addGrade`、`editGrade`、`reviewGrade`、`getGradeLevel`）。
- 时序图的生命线从左到右：actor → 编排者 → 领域对象。返回给 actor 的最终结果是一条编号消息。
- 活动图的失败路径汇入唯一终点。泳道用 Teacher、Grade、Academic Admin 这类名字，不用 System。

第二条必须写进测试和评估的失败/伦理路径：**学生不能修改他人成绩，班主任不能编辑分数**。这是权限，不是界面装饰。

## 问题域和界面域怎么分开写

现在规则大多写在 store 和页面组件里。开发阶段报告这样指认，直到代码被拆开：

- **问题域**：`src/types/index.ts` 的类型与状态机（`GradeStatus`、`AppealStatus`）；`src/data/mockData.ts` 的 `getGradeLevel`；`useGradeStore` / `useScheduleStore` 里不依赖 JSX 的更新函数。
- **界面域**：`src/pages/**`、`src/components/**`、路由守卫 `ProtectedRoute`。

若把等级计算、分数范围、状态转换抽成纯函数，在类图补上该模块，并给这些函数写测试。抽取之后，计划报告的设计节要有一句「实现时将 X 从页面移到 Y」，评估的修改节引用这句。

## 错误处理证据

已经能写进测试的失败点（以代码为准，消失了就删掉这条）：

- 登录缺用户名或密码，或口令与身份不匹配。
- 学生注册：必填项、两次口令不一致、口令长度。
- 登记成绩时的空选择或越界分数（打开 `GradeRegister.tsx` 确认当前校验，不要沿用这份清单里已经过时的句子）。
- 越权路由：非教务访问 `/grades/edit/:id`、`/schedule/arrange`、`/exam`、`/users` 会被带回首页。

每一条写成测试用例：角色、路径、输入、期望看到的提示或跳转、实际结果、日期。

## 伦理（个人数据）

成绩、班级、身份证号（注册表单里的 `idCard`）属于个人数据。报告里写清：

- 谁可以读、谁可以改，对应上表。
- 口令出现在客户端持久化里，这是当前控制的缺口。
- 路由守卫只在界面层。熟悉浏览器存储的人可以改本地数据。评估的缺点和后续开发要提到服务端校验，并说明本次范围不做。
- 申诉若使用固定授权码，写明码从哪来、谁可以使用，以及硬编码授权码的风险。

## 用户文档骨架

按角色各写一节，每节只写该角色做得到的事：

1. 如何打开系统、如何选择身份、如何登录、失败时看到什么。
2. 学生：看成绩、看课表、发起申诉、改个人资料。
3. 任课老师：登记成绩、看相关成绩、处理申诉、看课表。
4. 班主任：看本班成绩、复核、处理本班申诉、看班级课表。写明不能改分、不能排课。
5. 教务：改分、复核、排课、考试、用户、申诉。

步骤里的按钮文字与页面上的中文一致。截图从一次真实操作来，文件名带日期。

## 评估里建议如实写出的缺点

这些是代码里已经存在的事实，用来写「缺点」和「以后的开发」，不要在评估里把它们说成已经解决：

- 数据停在浏览器本地，换一台电脑就没有了。
- 口令和授权码在客户端。
- 问题域与界面还没有完全分开。
- 架构文档与实现不一致时，以 `src/` 描述系统，并把文档过时写成过程里的一次发现（如果考生确实发现了）。

优点只写能指给阅卷人看的行为：四种角色的成绩视野不同、复核状态、申诉流转、排课仅教务可用。
