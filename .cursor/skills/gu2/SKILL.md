# GU2 —— 大综合 2（H48W 35）

本 skill 服务这一门课、这一个项目：

- 单元：**Computing: Software Development: Graded Unit 2**，代码 **H48W 35**（2018 年 7 月，version 03）。中心叫它「大综合 2」或 GU2。
- 领域：教务（学生、班级、课程、成绩、考核或考试、管理员）。本仓库的 React 原型是行为参照，见 `references/edu-system.md`。它是不是被评分的那份实现，由任务书和会议纪要决定。
- 官方最低证据在 `references/evidence.md`。今年中心口述、以及哪些话还不能当成课件原文，在 `references/center-notes.md`。别的课的最低线在 `references/boundaries.md`。

提交件必须是考生本人能在进度面谈里讲清楚的工作。本 skill 补证据、对齐名称、指出缺项。它不替考生做设计决定，也不帮任何人绕过原创声明或中心的学术规范。引用了规范、库或他人材料，就写进参考文献。

## 开工

1. 问清阶段：Planning / Developing / Evaluating。上一阶段的最低证据和该阶段至少 50% 都达到，才能做下一阶段。计划还没过，不要写「开发已完成」。范老师在第一部分给的是 S / RD / RA / RT，不是 A/B/C。
2. 读 `references/center-notes.md` 和 `references/edu-system.md`。PRD 和架构文档落后于代码，不要当现状。
3. 锁定追溯链，后文名字都从这条链上取：

   项目简报 → 四个子系统（或纪要写明的三个）→ 功能需求、非功能需求、隐含要求、数据实体 → 顶层用例 → 会议纪要里的语言和范围 → 分析设计 → 被评分的代码 → 测试 → 评价里的满足 / 未满足。

4. UML 用用户 skill `drawio-uml-gen`：先写 spec JSON，再跑生成器。页面设计可以手画，不要用 HTML 充当设计图。任务书没点名的图不要为了凑连连看的六件套去画。

## 这份证据长什么样

书面部分合成**一个文档**，三阶段的内容都在里面。不要拆成二十多个文件的压缩包。代码单独能被抽查，不要理解成「只交 Word、不交实现」。

文档里至少要有这些块。模板的标题以文件夹为准；文件夹没打开时，用下面这些，老师已经给过的标题不要改词：

- 封面：只有文字，全部居中，字号一致。不要在封面上堆内容。
- 项目简报解读、功能需求、非功能需求、信息来源（指向文末文献表）
- 隐含要求，以及数据实体：student、班级、课程、管理员各自收集什么
- 顶层用例，每条用例落在某个子系统上
- 项目计划：阶段时间、里程碑、交付物、主要任务、资源。计划阶段的任务里不要夹开发任务
- 会议纪要：语言及理由写在纪要之后；若只做三个子系统，写明主席的意见和三个名字
- 分析与设计
- 开发证据、测试计划、测试运行、用户文档
- 评价五段

代码贴进文档的字体和行距以第一次课课件为准。课件未读就标成缺口，不要自拟一套格式。

## 三阶段各写什么

分数和最低证据见 `references/evidence.md`。

### Stage 1 — Planning（40 分）

三块都要在，而且不能互相矛盾。

- **任务书分析（最多 14）**：用自己的话解释简报；功能需求、非功能需求、隐含要求、数据实体；顶层用例；为澄清题目看过什么、本项目不做什么；目标；资源从哪来；信息来源。
- **项目计划（最多 6）**：时间要和真实课时对得上。这不是项目管理导论那份近百条 WBS。开发阶段的任务名用课件里范老师写的前几项。
- **分析与设计（最多 20）**：用例、静态模型、关键用例的动态模型，都要对得上准备做的那三个或四个子系统。高分来自取舍和理由。只做一个子系统，结构不够。

顶层用例是用户目标，不是站点地图。本仓库里已经露出的目标（登录、查成绩、登记、修改、复核、申诉、处理申诉、课表、排课、排考、用户管理）可以当作简报尚未读到时的起点。注册和修改密码在原型里没有做完，不能写成已实现。简报里的四个子系统名字一旦从文件夹读到，用例按子系统重划，不要留着一份对不上的清单。

### Stage 2 — Developing（40 分）

先确定哪一份代码被评分。

- 会议纪要写的是 C#（或任务书写的别的语言）：作品集对着那份实现。本仓库只用来核对成绩、角色和申诉应该怎么表现，不能把 React 路由写成那份实现。
- 任务书明确接受这个网页原型：问题域、界面、路由以 `references/edu-system.md` 为准。评价里写明没有按 stage 2 的 ORM 要求做数据库，这一项未满足。

无论哪一份实现，作品集都要看得到：问题域、界面、自己查过的库或语法、错误处理、内部文档、测试计划、测试运行、用户说明。测试运行要有输入、期望、实际、结论。截图从运行中的系统截，图里不要带聊天窗口。

若被评分的是带数据库的 C# 或 Java：数据访问用 ORM，把对象存进数据库，不要在界面里写 SQL。若被评分的是本仓库：zustand、React Router、Tailwind 可以写进「自己查过的库」，但要说明哪一部分是自学的。`edu-system.md` 末尾的已知缺陷必须出现在测试或缺陷记录里，修了就回归，没修就标未修复。

### Stage 3 — Evaluating（20 分）

五段都要指回需求编号和测试编号：

- 简报要求什么，方案逐条满足到哪
- 优点和缺点
- 以后改什么，以及为什么是这些
- 中途改了什么。只做三个子系统的那句主席意见，改语言、改任务划分，都写在这里。RD 之后返工过，也写在这里
- 长了哪方面的知识和技能，过程本可以怎样更好

缺点里要看得到真实缺口：原型没有数据库和 ORM、密码在客户端、注册不能登录、修改密码不生效、考试种子数据对不上。不要把没做的写成已完成。

伦理放进评价或任务书分析：成绩和个人信息谁能读、谁能改；教学原型把密码放在浏览器里，正式系统不能这样。

## 作品集检查

`scripts/check_portfolio.py` 在文件名和文档正文里找章节，不判断分数。docx 会读正文，pdf 只看文件名。

```bash
python scripts/check_portfolio.py PORTFOLIO
python scripts/check_portfolio.py PORTFOLIO --manifest slots.json
```

退出码 0 表示章节都找得到，1 表示有缺项，2 表示路径不是目录。文件很多时它会提醒「二十多个松散文件曾被看成没按要求」，这个提醒不改变退出码。

## 做完的定义

交给考生定稿之前：

- 该阶段 `references/evidence.md` 的每条最低证据都有章节，没有的标成缺口
- 子系统、用例、类名、角色在文档、图和被评分的代码里是同一套
- 只做三个子系统时，会议纪要里有主席意见和三个名字
- 数据实体写了四类角色各收集什么；语言和理由在会议纪要之后
- 评价里每一条「已满足」能指到测试；已知缺陷没有写成已修复
- 参考文献覆盖 H48W 35、用到的库、背景调查里的同类系统
- 考生能不看稿说明：四个子系统是哪几个、为什么是三个还是四个、谁可以改成绩、数据怎么进数据库

## 不要做

- 不要把连连看的六件套最低线、项目管理导论的百条 WBS、面向对象分析与设计的扣分细则当成 GU2 的评分表。
- 不要编封面字号以外的版式，也不要编代码贴进文档的格式。那些在未读的课件里。
- 不要把「检测率低于某个百分数」写成过关标准，也不要写如何把检测率压下去。范老师会读讨论，也会在面谈里问。
- 不要把别人的 GU2、去年的模板正文改写成这份作业。去年的东西老师说过可以参考，但今年格式不一样。
- 不要替考生签原创声明。声明按考生自己的学号签。
- 不要把演示账号和写死的授权码写进面向真实学校的部署说明。
